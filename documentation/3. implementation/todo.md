| S24 | 🐞 **BUG — `specstore.List` has no default cap, so a caller who names no limit gets the whole live table back in one response.** `List[T any](st *Store, q *gorm.DB, role string) ([]T, error)` (`specstore/store.go:127`) runs whatever query it is handed — `q.Find(&rows)` — and applies no `.Limit(...)` of its own; nothing else in `specstore` or `dispatch` supplies a default either (confirmed: `grep -rn "Limit\|MaxPage" specstore/*.go dispatch/*.go` outside tests turns up only the unrelated `Limit(1)` inside `Take`). Demonstrated live against the package's own fixture domain (`store_test.go`'s `ticket` role): seeded 150 tickets, called `specstore.List[Ticket](st, st.Query(ctx, roleTicket), roleTicket)` with no `.Limit` on the query — real output: all 150 rows returned in one `[]Ticket`. Every module built on this engine inherits the gap by construction unless its own `List<Type>` remembers to add `.Limit(...)` itself: `mwanachama-backend-agency`'s 18 `List<Type>` methods (`store.go`'s `list[T]` helper, a thin wrapper over `specstore.List`) never do, and this is the same shape already demonstrated live against that library (`ListRoles` returning 800 of 800 seeded) and filed — on the wrong board, against the wiring repo rather than the code that is actually wrong — as `mwanachama-wakala-api`'s WK36. **Checked and does not extend to `mwanachama-backend-permissions` or `mwanachama-backend-catalog`**: both hand-roll their own `q.Find(&rows)` (`role.go`/`grant.go`; `entry.go`'s `ListEntries`) rather than calling `specstore.List` at all (`grep -rn "specstore.List\b"` across both, non-test, empty) — each has its own independent instance of the same loophole class instead, filed on its own board (`mwanachama-backend-catalog`'s CAT10; `mwanachama-backend-permissions`'s PM8). **Fix location**: `specstore.List` itself, which covers every present and future consumer that calls it (today, only `mwanachama-backend-agency`'s `list[T]`) in one place. | 📋 | — |
| S28 | ⚠️ **An index name repeats its whole table name, so neither catalog nor taskmanager can take a second mount at all against a real instance slug.** `IndexFor` is `TableFor(o) + "_" + idx.Name + "_idx"` (`spec/spec.go`), and Postgres keeps indexes in the same 63-byte namespace as tables. Measured against the real slug `mwanachama-wakala-api` mints (`tableSlug()` = `"agy"` + 8 hex = 11 chars), the longest identifiers shipped today are already **62 of 63** (`<slug11>_catalog_suggestion_comments_suggestion_created_idx`) and 61 (`<slug11>_taskmanager_workflow_runs_parent_workflow_run_idx`). S26's mount segment costs `len(mount)+1`, so catalog admits no second mount and taskmanager admits only a one-character one — verified live, not computed: `catalog.ParseSpec` refuses even a 1-character mount at 64 bytes, and `taskmanager.SpecForMount("wakala","supplier")` refuses at 65. **This is safe, just limiting** — `Validate`'s `claim` measures every emitted name and refuses at load, naming the index and the byte count; nothing truncates. The fix is to stop spending the budget on readability the database does not need: an index name only has to be unique database-wide, so `<instance>_<module>_<mount>_<n>_idx` with a short digest of the table, or a digest suffix on a truncated name, buys back ~20 bytes permanently. ⚠️ **It renames every index in every live database**, so it wants the same treatment as `mwanachama-wakala-api`'s WK54 and is a decision, not a cleanup. **Headroom per module, measured against the real 11-char slug** (`63 - worst - 1`, since a mount costs `len(mount)+1`): catalog **none** (62/63) · taskmanager **1 char** (61) · permissions 9 (53) · accounting 12 (50) · actor 11 (51) · workspace 11 (51). ⚠️ Short fixture instance names hide this — taskmanager's own tests pass a 6-character mount because `wakala` is 5 bytes shorter than a real slug. Measure against a real slug. Until S28 lands, catalog and taskmanager are single-mount by construction. (`mwanachama-backend-actor` joined the declared-domain set 2026-09-29 in a concurrent session and already ships `SpecForMount`; comm and forms declare no indexes in their shipped examples, so they are unmeasured here.) | 📋 | S26 |
