| S24 | 🐞 **BUG — an operation can declare a `caller`-sourced overwrite and a `path`-sourced overwrite on the same field, and the dispatcher accepts it with no error, silently letting the one declared last win at runtime.** `dispatch/spec.go`'s `Operation.validate` counts overwrites (`overwrites++`) for both a `{"from":"caller","into":X}` argument and a `{"from":"path","into":X}` argument, but never checks whether two arguments name the *same* `X` — every other kind of declaration ambiguity this file catches (two operations claiming one action, two claiming one tool name, two arguments both landing as the same tool-schema key) has a `seen`/`first, taken` guard; this one does not. **Demonstrated**: `dispatch.Parse` on an operation with args `[{"from":"body","whole":true},{"from":"caller","as":"actor","into":"Name"},{"from":"path","as":"slug","into":"Name"}]` returns `err = <nil>` — the spec loads clean. Dispatching it and calling `PUT /records/attacker-controlled` with body `{"slug":"attacker-controlled","name":"whatever-body-said"}` against a mount whose `Deps.Caller` returns `"trusted-caller"` produces `status=200 body={"slug":"attacker-controlled","name":"attacker-controlled"}` — the caller-derived value is overwritten a moment later by the path segment, because `overwrite`/`overwriteFromArgs` (`dispatch/dispatch.go`, `dispatch/tools.go`) just loop `op.Args` in declared order and the last `Into` write wins with `field.Set(v)`. Reversing the two arguments' order in the same spec (`path` before `caller`) instead produces `Name="trusted-caller"`, confirming declaration order alone decides the outcome with no signal at load time either way. **Why it matters**: `{"from":"caller","into":Field}` exists specifically (S23, extended for `mwanachama-backend-permissions`' PM5) so a domain can bind an actor/audit field from the authenticated identity a mount supplies, immune to whatever the request claims — [2. design/dispatcher.md](../2.%20design/dispatcher.md) says so in as many words ("into therefore accepts path and caller and nothing else: those are the two things that may outrank the body"). This gap means declaring *both* on the same field — plausibly by accident (a copy-pasted arg left in place while adding the caller one) rather than by malice — reopens exactly the server-owned-field-injection hole PM5 filed against `mwanachama-backend-permissions`' `create_grant`, and `Validate()` gives no warning that the protection is not actually in force. Not exploited by any operation shipped in `mwanachama-backend-catalog`'s `catalog.operations.json` (its one `{"from":"caller",...}` argument, `issue_share_link`'s `by`, is positional with no `into`) or by `mwanachama-backend-agency`/`mwanachama-backend-permissions` today — this is a latent engine defect, not a live exploit, and the highest-risk moment is `mwanachama-backend-permissions` landing PM5's own fix using this exact mechanism. **Fix location**: `dispatch/spec.go`'s `Operation.validate` — track `Into` targets in a `seen`/`first, taken` map the same way `seenAction`/`seenTool` already work, and refuse a second argument (caller or path) claiming a target already claimed. Red test (leave red until fixed): `dispatch/overwrite_conflict_test.go`'s `TestS24_OpenBug_DuplicateOverwriteTargetIsRefusedAtLoad`. Found 2026-09-27 by the scheduled integration-test sweep, examining `9272c53` ("caller arguments overwrite fields in operations") closely per that sweep's own instruction to scrutinize this exact loophole class. | 📋 | — |
