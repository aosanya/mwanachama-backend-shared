| S24 | 🐞 **BUG — `specstore.List` has no default cap, so a caller who names no limit gets the whole live table back in one response.** `List[T any](st *Store, q *gorm.DB, role string) ([]T, error)` (`specstore/store.go:127`) runs whatever query it is handed — `q.Find(&rows)` — and applies no `.Limit(...)` of its own; nothing else in `specstore` or `dispatch` supplies a default either (confirmed: `grep -rn "Limit\|MaxPage" specstore/*.go dispatch/*.go` outside tests turns up only the unrelated `Limit(1)` inside `Take`). Demonstrated live against the package's own fixture domain (`store_test.go`'s `ticket` role): seeded 150 tickets, called `specstore.List[Ticket](st, st.Query(ctx, roleTicket), roleTicket)` with no `.Limit` on the query — real output: all 150 rows returned in one `[]Ticket`. Every module built on this engine inherits the gap by construction unless its own `List<Type>` remembers to add `.Limit(...)` itself: `mwanachama-backend-agency`'s 18 `List<Type>` methods (`store.go`'s `list[T]` helper, a thin wrapper over `specstore.List`) never do, and this is the same shape already demonstrated live against that library (`ListRoles` returning 800 of 800 seeded) and filed — on the wrong board, against the wiring repo rather than the code that is actually wrong — as `mwanachama-wakala-api`'s WK36. `mwanachama-backend-permissions`'s `ListRoles`/`ListGrants` go through the identical `specstore.List` path. **Fix location**: `specstore.List` itself, so every consumer is covered in one place rather than eighteen-plus call sites across three repos each remembering their own cap. | 📋 | — |
