| S17 | 🐞 **BUG — `dispatch.Dispatch`'s HTTP routes accept and forward a caller-forged read-only field (`id`, `created_at`, ...) that the same spec's `dispatch.Tools` MCP surface correctly refuses.** `dispatch/tools.go`'s `flatten`/`schemaFor` skip a field marked `ReadOnly` in `Deps.Fields` when building an MCP tool's `InputSchema`, and `invokerFor`'s `known` map (built from that same filtered `props` list) makes `Invoke` refuse any caller-supplied key not in it — demonstrated live: `tools[0].Invoke(ctx, {"id":"attacker-chosen-id","created_at":"1999-01-01T00:00:00Z","name":"Alpha"})` returns the error `t_record_create takes no argument "id"`. But `dispatch.go`'s `Dispatch`/`handlerFor`/`bind`/`wholeBody` — which builds the HTTP route from the *exact same* `Spec` and `Deps` (including the same `Fields` map) — never reads `Deps.Fields` at all (`Fields` appears in `dispatch.go` only once, in the `Deps` struct's own field declaration; `bind(op, t, r)` and `wholeBody(want, r)` take no `Deps`/`Fields` parameter, so a `ReadOnly` fact known to the same spec is architecturally unreachable from the HTTP binder). Demonstrated live over real HTTP: the identical `Deps{Manager, Fields}` dispatched to routes, `POST /records` with body `{"id":"attacker-chosen-id","created_at":"1999-01-01T00:00:00Z","name":"Alpha"}` → `200 {"id":"attacker-chosen-id","created_at":"1999-01-01T00:00:00Z","name":"Alpha"}`, and the manager's `Create` receives `{ID:attacker-chosen-id CreatedAt:1999-01-01T00:00:00Z Name:Alpha}` — the forged id and timestamp landed verbatim. This defeats the exact security property `documentation/2. design/dispatcher.md` claims for `ReadOnly`: "A field the store owns — a primary key, a stamped time... is marked read-only and never becomes an argument. That is what keeps `catalog_entry_upsert` from offering a model a `visibility` it would be entitled to expect the store to honour" — that sentence is true for the MCP tool surface and false for the HTTP route surface built from the same declaration. This is the same server-owned-field-injection shape already found (and, per `mwanachama-backend-agency`'s AG21, fixed at the manager level) as `mwanachama-backend-actor`'s ACT4 and `mwanachama-backend-forms`'s F4 — except `dispatch` is brand-new shared infrastructure (`bb2a4c3`/`81e1c66`, 2026-09-23) explicitly built to *replace* the hand-written route tables in actor/assetmanager/comm/forms/git (`httpwire`'s own package doc, quoted in the dispatcher design doc), so every future adopter inherits this hole through the binder itself, silently, regardless of whether that adopter's manager clears the field the way AG21's fix does — the one place this package claims to guarantee the property (`Deps.Fields`'s `ReadOnly` flag) does not reach the HTTP path at all. Not yet reachable through any live deployment: fleet-wide grep (`grep -rl "backend-shared/dispatch" --include="*.go"` across all sixteen other repos) found zero consumers as of this sweep — `dispatch` is not wired into any route table yet — so this is a defect in unreleased infrastructure, not a live production hole. Defect location: `dispatch/dispatch.go`'s `bind`/`wholeBody`/`wholeQuery`/`Dispatch`/`handlerFor` — none of them thread `Deps.Fields` through the way `tools.go`'s `flatten`/`invokerFor` do. Pinned by `dispatch/s17_readonly_pin_test.go`'s `TestPinsS17_MCPRefusesAReadOnlyFieldTheHTTPRouteAccepts` — asserts the MCP tool refuses the forged fields (as today) and the HTTP route currently accepts them with status 200 and the forged values landing on the manager; the HTTP-side assertions must go red once `bind`/`wholeBody` are made to consult `Deps.Fields` the way `tools.go` already does. | 📋 | — |
