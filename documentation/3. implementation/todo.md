| S23 | 🐞 **BUG — `spec.Migrate` runs DDL for a spec `s.Validate()` itself refuses, silently merging two declared objects into one physical table.** Two objects (roles or plain domain objects) that name the same physical table — the exact "silent data mixing" scenario `declared-domains.md` warns about — are caught by `(*Spec).Validate()`, but `spec.Migrate(db, s)` never calls `Validate` itself, so a `*Spec` reaching `Migrate` any way other than through `Load`/`Parse`/`Blueprint.Load`/`Blueprint.Parse` gets zero protection. Reproduced live: a hand-built two-object spec (`bin`/`pallet`, both declaring table `"bins"`) is refused by `s.Validate()` with `table "bins" is declared by more than one object`, but `spec.Migrate(db, s)` on the same spec returns `nil` and silently creates `acme_inventory_bins` with only the first object's columns (`[id capacity]`) — `pallet`'s `weight` column never exists, and any code that later writes a `pallet` row through this table does so against `bin`'s schema with no error anywhere. `specstore.New` has the identical gap (it checks spec-vs-carrier agreement only, never calls `Validate`). The asymmetry is demonstrable in the same codebase: `dispatch.Dispatch`, `dispatch.Parse` and `dispatch.Tools` all defensively re-`Validate()` the spec they are given before using it (`dispatch/dispatch.go:45`, `dispatch/spec.go:84`, `dispatch/tools.go:51`) — `spec.Migrate` (`spec/migrate.go:14`) and `specstore.New` (`specstore/store.go:22`) do not. Reproduced by `TestS23_OpenBug_MigrateRefusesAnInvalidSpec` (`spec/migrate_openbug_test.go`). **Affects every consumer that builds or mutates a `*spec.Spec` other than by re-parsing it before migrating** — `mwanachama-backend-catalog`, `mwanachama-backend-agency` (AGD-007) and `mwanachama-backend-permissions` all call `spec.Migrate`/`specstore.New` directly and would get the same silent behaviour if any future code path (a merge, a programmatic spec, a test helper) hands either function a spec that skipped `Load`/`Parse`. | 📋 | — |
| S24 | 🐞 **BUG — `dispatch`'s whole-query binding derives a query-parameter name from the lowercased Go field name, ignoring the field's own `json` tag, so a caller filtering by the field's documented (response-body) name is silently ignored.** `wholeQuery`'s `queryKey(f reflect.StructField)` (`dispatch/dispatch.go:307`) only ever checks a `query` struct tag, falling back to `strings.ToLower(f.Name)` — it never reads `json`, even though whole-body binding (`wholeBody`, the same file) goes through `encoding/json` and does respect it. Any filter struct with a multi-word field (`RoleCode string \`json:"role_code"\`` — found downstream in `mwanachama-backend-permissions`'s `GrantFilter`, filed there as PM6) silently binds to `rolecode`, never `role_code`, so a request using the field's own documented spelling matches nothing and the filter is silently skipped. Reproduced directly against `dispatch` with a fresh fixture (no consumer repo involved): `WidgetFilter{WidgetCode string \`json:"widget_code"\`}`, two widgets seeded (`code=a`, `code=b`), `GET /widgets?widget_code=a` — real output: `status=200 widgets=[{Code:a} {Code:b}]`, both returned, not just the filtered one. Reproduced by `TestS24_OpenBug_QueryKeyIgnoresTheFieldsJSONTag` (`dispatch/bind_openbug_test.go`). Fix location: `queryKey` should fall back to a field's `json` tag before its lowercased Go name, the same precedence `wholeBody`'s `encoding/json` decode already gives it. **Affects every consumer using a whole-query filter struct with a multi-word field** — `mwanachama-backend-catalog`, `mwanachama-backend-agency` and `mwanachama-backend-permissions` should each be checked for the same shape once this is fixed here. | 📋 | — |
| S25 | 🐞 **BUG — `bind()` never enforces a declared `Arg.Required`, so a named body field an operation declares required is silently bound to its zero value when the caller omits it — while the MCP-tool invocation path for the identical declaration does refuse it.** `bindOne` (`dispatch/dispatch.go:335`, the `default:` case for a named, non-whole body field) reads `body[a.As]`; when the key is absent it returns `reflect.Zero(want), nil` unconditionally — `a.Required` is never consulted anywhere in `dispatch.go`. Contrast `tools.go`'s MCP invocation path, whose `TestAMissingRequiredArgumentIsRefused` confirms a missing required argument is refused with `needs "<field>"` for the same `Arg.Required: true` declaration — the same spec produces two different behaviours depending only on which transport dispatched it. Found downstream in `mwanachama-backend-permissions`'s `set_actions` operation (missing `actions` field on `PUT`, filed there as PM7: the caller's role is silently wiped to `[]` and immediately locked via `seeded=true`), but the gap is `dispatch`'s own, not that operation's. Reproduced directly against `dispatch` with a fresh fixture: op `rename_thing` declares `{"from":"body","as":"name","required":true}`; `PATCH /things/t1` with body `{}` — real output: `status=200 thing={ID:t1 Name:}`, the thing silently renamed to an empty string with no error at any point. Reproduced by `TestS25_OpenBug_BindNeverEnforcesArgRequired` (`dispatch/bind_openbug_test.go`). Fix location: `bindOne`'s `default:` case (and `wholeValue`/`wholeBody` for a whole-body arg, which has the identical gap for a struct field the *type's own* schema marks required) should refuse with a `needs "<field>"`-shaped error the same way `tools.go` already does, rather than leaving every HTTP-facing required-field guarantee to be reinvented per manager method. **Affects every consumer declaring a required body-field operation** — `mwanachama-backend-catalog`, `mwanachama-backend-agency` and `mwanachama-backend-permissions` should each be checked for the same shape once this is fixed here. | 📋 | — |
