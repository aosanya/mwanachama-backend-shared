| S23 | 🐞 **BUG — a declared tool name is not checked against another operation's default derived name, so `dispatch.Tools` can silently publish two tools with the identical name.** `Validate`'s `seenTool` map (`dispatch/spec.go:101,127-136`) is only populated when an operation explicitly sets `"tool"`; an operation that leaves `Tool` empty gets its default name (`toolName(op.Action)`, `dispatch/tools.go:116`) with no entry in `seenTool` at all, so nothing checks a later explicit declaration against it. Demonstrated with two operations, `open_entry` (action `x.entry.open`, no declared tool — default name `x_entry_open`) and `fetch_entry` (action `x.entry.fetch`, `"tool":"x_entry_open"`): `dispatch.Parse` accepts the spec and `dispatch.Tools` returns two `Tool` values, both `Name: "x_entry_open"`, with no error from either call. Every other uniqueness check in the same function (`seenAction`, `seenAddress`, `seenOnce`) has no "derived default" half to miss, which is why this is `Tool`'s own gap, not a pattern repeated elsewhere in `Validate`. S22 (2026-09-24) added exactly the declared-name feature this defect sits in, for a module converting a hand-written MCP surface whose callers already hardcode a name (`mwanachama-backend-agency`'s AG41) — the same situation where a converting module is most likely to pick a declared name that collides with an unrelated operation's default. Matters for `mwanachama-backend-agency`'s `mcp/` (generated from `agency.operations.json` through this dispatcher) and any future catalog/wakala-api MCP surface converted the same way: two same-named tools reaching `mcp.AddTool` depend on that SDK's own collision behaviour (silent overwrite or panic, not verified here — out of scope for this repo). Pinned by `TestS23_PinsKnownDefect_DeclaredToolNameNotCheckedAgainstDerivedNames` (`dispatch/s23_tool_collision_test.go`) — currently green, asserting the *current* (broken) behaviour; it goes red once the fix makes `seenTool` also check against every operation's derived default name (or the equivalent) and `Validate` refuses the collision the same way it already refuses two explicit declarations of the same name. | 📋 | — |
