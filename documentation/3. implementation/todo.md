| S23 | 🐞 **BUG — `spec.Migrate` runs DDL for a spec `s.Validate()` itself refuses, silently merging two declared objects into one physical table.** Two objects (roles or plain domain objects) that name the same physical table — the exact "silent data mixing" scenario `declared-domains.md` warns about — are caught by `(*Spec).Validate()`, but `spec.Migrate(db, s)` never calls `Validate` itself, so a `*Spec` reaching `Migrate` any way other than through `Load`/`Parse`/`Blueprint.Load`/`Blueprint.Parse` gets zero protection. Reproduced live: a hand-built two-object spec (`bin`/`pallet`, both declaring table `"bins"`) is refused by `s.Validate()` with `table "bins" is declared by more than one object`, but `spec.Migrate(db, s)` on the same spec returns `nil` and silently creates `acme_inventory_bins` with only the first object's columns (`[id capacity]`) — `pallet`'s `weight` column never exists, and any code that later writes a `pallet` row through this table does so against `bin`'s schema with no error anywhere. `specstore.New` has the identical gap (it checks spec-vs-carrier agreement only, never calls `Validate`). The asymmetry is demonstrable in the same codebase: `dispatch.Dispatch`, `dispatch.Parse` and `dispatch.Tools` all defensively re-`Validate()` the spec they are given before using it (`dispatch/dispatch.go:45`, `dispatch/spec.go:84`, `dispatch/tools.go:51`) — `spec.Migrate` (`spec/migrate.go:14`) and `specstore.New` (`specstore/store.go:22`) do not. Reproduced by `TestS23_OpenBug_MigrateRefusesAnInvalidSpec` (`spec/migrate_openbug_test.go`). **Affects every consumer that builds or mutates a `*spec.Spec` other than by re-parsing it before migrating** — `mwanachama-backend-catalog`, `mwanachama-backend-agency` (AGD-007) and `mwanachama-backend-permissions` all call `spec.Migrate`/`specstore.New` directly and would get the same silent behaviour if any future code path (a merge, a programmatic spec, a test helper) hands either function a spec that skipped `Load`/`Parse`. | 📋 | — |
